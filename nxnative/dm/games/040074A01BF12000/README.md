# Donkey Kong Bananza (`040074A01BF12000`)

A Switch 2 game: update v458752 over the base game, SDK 20.5.19 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive), modules `main` + `sdk`. **Plays on the Mac** (M4 Pro): three play sessions of about 5 minutes each and scripted runs of up to 15,900 frames, through the opening, the mining tunnel and the areas after it, with the guide movies in their panel, at 60 fps; in busy scenes the game drops itself to 30 fps for a few seconds ([Open](#open)). The first start with no pipeline archive builds the pipelines for about 4 minutes, once. The Mac tests cover only the first level's opening areas. An initial [community iOS report](#ios-community-report) is recorded below.

## iOS community report

[Issue #1183](https://github.com/seedds/nxnative/issues/1183) reports a successful nine-minute session (33,600 frames) on an iPhone 18 Pro (`iPhone19,2`), iOS 27.2 (`24B119`), with update v458752 and one DLC. This is a community report on commit `d145b9563063`, shader chain `09e6fcbd87b8`, not a test of current main. The app was built from a dump folder with `--platform ios --prepare-xcode` and signed through Xcode with Increased Memory Limit; settings were defaults plus `DM_METAL_HUD=1`, with Low Power Mode off.

- No crash or `[RED]` line was reported. The opening minutes ran at about 60 fps; after thermal state reached 2, most windows ran at 45–60 fps, with a session average of 50.5 fps. One stretch ran at 30 fps; its cause was not checked.
- Peak reported footprint was 5,575 MiB. Loads and area changes had frame-time p99 spikes of 50–166 ms.
- Coverage is limited to this device, build and short session. Longer play, current main and other iOS devices remain unvalidated.

## Files

- Built from a dump folder (`base/`, `updates/458752/`, `dlc/040074a01bf13001/`): `build_ipa_from_nsp.py <folder> --platform mac-app` packs it with [`scripts/pack_dump.py`](../../../scripts/pack_dump.py), with no keys; the app has no icon, as a dump has no control data. The update's RomFS is the patched one (80,273 files, 8.6 GB; it drops 42 base files, among them the `Product.100` tables its `Product.200` ones replace), so it is packed on its own. The DLC (add-on content index 1, 8,000 files, 0.9 GB) mounts as `EmeraldRush`.
- Shaders: `Shader/*.Nin_Ounce_NVN2.bfsha.zs` (BNSH) and `Shader/Project.Nin_Ounce_NVN2.release.sarc.zs`. The code is Volta / Ampere's 128-bit encoding (`0x794d` EXIT, `0x7918` NOP), not Maxwell's.
- NVN2 control sections (dumped with `DM_NVN_SHDUMP`): magic `0x98761234`, version `0xc9`; +0x38 the instructions' length (SPH included), +0x40 that rounded to 0x100, +0x44 the code area's (the c1 segment lies between the two), +0x4c the register count, +0x58 compute's thread group. Their own length is at +0x30 in BNSH files only (0xd8; 0xd0 in effects, 0 in agl's BAHS and in memory), so the shader key hashes the first 0x48 bytes with +0x30 zeroed, plus the code area (`hle_nvn.c` `nvn_ctl_lens`, `shader_split.py` `key_ctl`).
- agl's upscaler is an `NDSR` pack, `agl_ndsr.pck` in `Lib/agl/agl_resource.Nin_Ounce_NVN2.release.sarc.zs`: 16-byte records from +0x10 (control section offset, control length << 4 | type, code offset, code length / 16 << 8 | type) up to a zero one; 30 shaders (3 vertex, 3 pixel, 24 compute: a small network on the tensor cores, HMMA, LDSM, MOVM). `shader_split.py` `ndsr_shaders` reads it, and pairs each vertex record with the pixel record after it. All 24 compute variants encode linear input; they come in threes by output: encoded output, linear output with neural luma clamped to 0–1, and linear output with neural luma clamped to 0–128 ([An upscaler's colour read from its code](../../../docs/reference/rendering.md#an-upscalers-colour-read-from-its-code): MetalFX draws the 16 linear ones, the 8 others keep the network; not run on the game since, as its libraries are of an earlier chain).
- The split reads the bfsha / BNSH files, agl's BAHS archives (`agl_common.sharcb` and the others: 1,555 shader records, one more than the archive counts, so the record check allows 1 % of strays) and sead's primitive drawer: 22,852 shaders (with the 30 of the NDSR pack).
- [`geo_mesh.tsv`](geo_mesh.tsv): the game's one vertex / geometry pair (`f9c807930abd1234` with the passthrough kernel `5d537f7630ec3671`), which draws every geometry draw, about 600 a frame; built as a mesh library of 16 triangles a group ([Mesh geometry groups sized to the vertex output](../../../docs/reference/shaders.md#mesh-geometry-groups-sized-to-the-vertex-output)).
- The prewarm seed list, [`pso_manifest.tsv`](pso_manifest.tsv) (3,793 lines: 1,726 shaders, 2,030 render pipelines, 37 compute pipelines), is the Mac's device list of the play sessions before the host read device lists without a seed list ([development.md](../../../docs/development.md#prewarm-lists)): boot, the title, the opening and its guide movies, the mining tunnel and the areas after it, recorded with prewarm off. A start with no device list builds it in about 8 s before the first frame.

## Shaders

The translator decodes Ampere code natively (job `arch: sm86`; [Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2)): all 22,852 shaders translate (chain 6f41726ef36d). NVN2 keeps NVN's texture handle table in c[2] (0x20 + 8 slot) and the graphics stages' storage buffer tables in c[0] (0x110 vertex, 0x510 pixel); compute lays out c[0] per shader from its control section, push constants first ([Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2)). The upscaler pushes (1 / w, 1 / h, w, h) of its target for its graphics passes and the source and destination rectangles for its compute network.

## Rendering

The scene renders into 1676×943 targets (R11G11B10F colour), agl's upscaler takes it to 2304×1296, and that is copied to the 2880×1620 window. On the way to the first picture:

1. The upscaler's network did not translate (HMMA and the other tensor instructions): the window kept the output's clear colour (0.3, 0.3, 1).
2. Six effect compute shaders (`d076142721d836a5` and others) did not load: a storage address was a c[0] entry plus an offset from c[1], and the translator took the c[1] term as the base.
3. Black frames: the composite was cleared before the upscaler read it (`render_cond`, [What it needs](#what-it-needs)).
4. Black speckles and white blotches over a dark frame: NaN from the environment cube's mip chain ([Mip-chain pass sampling the level it renders](../../../docs/reference/rendering.md#mip-chain-pass-sampling-the-level-it-renders)). Found with raw dumps (`DM_NVN_SNAPRAW`) of the R11G11B10F targets, `DM_NVN_HILITE` to narrow the shaders (`cca896efc6bb7c21` and `c8637178e2818d18` wrote most of them), then those shaders' MSL instrumented to record their first NaN temporary: a fetch of the prefiltered cube, back through the prefilter to the cube's own mip passes.
5. Woven rock surfaces and holes in the rock: the textures the game loads were untiled in the Tegra X1's order inside a GOB ([The Switch 2's order inside a GOB](../../../docs/reference/nvn-objects.md#the-switch-2s-order-inside-a-gob)). The rock material's albedo (ASTC 8×8) written straight to its output looked right and its BC7 normal map did not, so the BC7 file (`BaseRock000_Pnrm`) was decoded offline in every order of the GOB's address bits.
6. The geometry shader `5d537f7630ec3671` (no vertex output: it writes its primitives to memory with ATOMG / STG) needed LEPC, OUT and ISBERD, and `7529699c7b7e49c0` (ActionLibraryPass compute) MATCH; with them all 468 shaders of the first gameplay minute translate.
7. Black tunnel walls and floor, with only the loose rocks and Donkey Kong drawn (compared with a YouTube capture of the same spot): the terrain's colour pass, about 400 indirect draws, drew nothing.
   - **How the terrain is drawn:** each chunk's depth prepass runs the culling geometry shader `5d537f7630ec3671`. It writes the surviving triangles' indices and adds their count to the chunk's indirect draw record (64 bytes, bound as its storage buffer 0). The colour pass draws from that record.
   - **What was wrong:** the records held instance count 0, and their counts grew frame after frame. Every frame gsys's vertex shader `c9a56f796ea4a4cd` (96 points or more) writes {count 0, one instance} into each record whose address its storage buffer lists. The translator had dropped those stores ([Global memory at an address loaded from memory](../../../docs/reference/shaders.md#global-memory-at-an-address-loaded-from-memory)).
   - **What NVN2 does:** decoding NVN2's indirect draw macro showed that instance count 0 draws nothing and the draw never resets the record.
   - **Now:** the walls, floor and lit passage draw as in the capture, at 60 fps.

## Boot (Mac)

Each step below stopped the boot before its fix:

1. `sdk: no SDK version string`: the version reads `nnSdk-Generic_20_5_19` (`loader.c` `dm_sdk_major` skips the variant name).
2. `GetInfo` 0x21, a Switch 2 info type: the kernel's page size. `nn::ro::ProtectRelro` takes value − 1 as the RELRO alignment mask; 0 aborted (`hle_svc.c` answers 0x1000). Type 28 is Horizon's AliasRegionExtraSize (0, named with 25–27 so that Switch 1 games print no new red line); 29–32 are the Switch 2's remote region: `nnosInitialize` builds `nn::os::detail::RemoteRegionManager`'s address space allocator over [type 29, type 29 + type 30), and `nn::os::GetRemoteMemoryUsage` returns types 31 and 32. Only the GPU driver's boot maps into it (`nv::InitializeGraphics` → `nn::gs::sdk::BootGraphicsSystem` → `BootWithRemoteMemory`), and the host replaces `nv::InitializeGraphics` (the overload with a pool, the one the game calls), so all four are 0: no remote region.
3. NVN2 reports API 231: the game requires major 231, minor ≥ 30 (`main+0x5c61a4`) and creates no graphics system otherwise (null read in its frame loop). `dm_sdk_ounce` (the sdk's `spec: Ounce`) selects 231.30 (`hle_nvn.c`).
4. 197 NVN2 entry points (ray tracing, mesh shaders, DLSS, device commands, HDR window metadata, a ProgramBuilder) were unknown names, so lookups returned null; they are in `names.txt` now, the unimplemented ones going to the red stub. Implemented: the ProgramBuilder (`nvnProgramInitializeFromBuilder` = Initialize + SetShaders), `QueueBuilderSetPrimaryQueue`, `CommandBufferSetRecordingMode` / `SetGeometryProcessingMode` / `SetComputeOverlapMode`.
5. Switch 2 SDK calls through services the host does not serve: `hid::InitializeJcms` and the Joy-Con mouse sensor (`hle_hid.c`), `oe::GetCurrentGraphicsScale` (`hle_oe.c`), `audio::IsDeviceOutputVolumeAutoTuneModeEnabled` (`hle_audren.c`), `streamplay` (GameShare, `hle_misc.c`), `vi` HDR / VRR / extended swap interval (`dm/gfx/hle_vi.c`).
6. `nv::InitCheck` (from `main+0xe19d04`, the start of a video decoder, after the first punch) tested the SDK's own flag, which `nv::InitializeGraphics` sets and the host's version of it does not: `hle_nv.c` answers it from the host's record. The same function then starts a video decoder: the Switch 2's `nn::codec` video API and sync point events, served on the host ([`nn::codec` video decoders taken over](../../../docs/reference/movies.md#nncodec-video-decoders-taken-over)).

## Android / Adreno 830 investigation (2026-11-07)

Current evidence from the Odin / Snapdragon 8 Elite, update 458752. Mac/Metal is the implementation reference; no matching Metal device frame was captured.

The candidate Android profile now records asynchronous replay, dynamic storage descriptors, ADPF target 90, 512-draw command-buffer cuts, 256-draw interior cuts including depth passes, GS claim bucketing, and cubic scaling for the 16 audited linear-output variants. Completed-frame ADPF remains off. These settings preserve the game's own pacing; the 90 target is an 11.11 ms work hint, not a 90 fps request. No root GPU-frequency floor, turbo, alternate shader probe, pass timestamps, descriptor profiler or CPU probe is included in the generated production environment.

The measured cave runs used the device's existing `docked=1` setting, with higher internal/output resolutions. The source and shader-derived profiles retain `docked=0` for first launch on the physical 1080p display; installer preserves existing user settings. A matched handheld comparison and final clean configuration validation are pending, so this profile update does not establish full-game or sustained handheld 60 fps.

- **Black Skills grid (resolved on Android, 2026-11-08):** the Skills menu's grid was opaque black squares: ui2d clears each medallion capture's rectangle with an alpha-0 quad that only Maxwell's alpha test keeps from drawing, and the Vulkan replay had no alpha test. [The alpha test in the Vulkan replay](../../../docs/reference/rendering.md#the-alpha-test-in-the-vulkan-replay).
- **Pink skin in shade (resolved on Android):** the 23,640-index `DKFoot_L` draw identifies `Mt_Skin`, fragment shader `c3631a6085cae513`. Its source `DonkeyKongNakedSkin_AlbMix` is authored deep red (sRGB8 166, 0, 27), while the base albedo is tan. The Vulkan backend fabricated every samples-passed report as `1 << 20`. `CubeMapDirector` divides five face-query counts by `5 * 128²`, so this became 64 in environment UBO5 +0x218. The skin's scattering multiplier includes `0.2/pi * (0.3 + 0.7 * E)`: the bad visibility value amplified the authored red term, which bypasses ordinary diffuse shadow/AO factors. Original NVIDIA instructions, SPIR-V and Metal agree on this math. CPU probes read the query helper's result -63 at `main+0x80dd78`, observed E=64 immediately after the writer at `+0x80dd7c`, and read 64 again before a later memcpy (64 hits each, captured during the Ingot Isle intro). Raw GPU probes independently read E=64 and the correct authored textures. [Real samples-passed reports](../../../docs/reference/rendering.md#numeric-visibility-from-real-vulkan-samples-passed-reports) replace that placeholder with precise cumulative Vulkan queries. The rebuilt runtime visibly restores tan hands, feet and ears in the escape-the-cave-in tunnel (`query-candidate-cave.png`, 2026-11-07). The post-fix raw GPU probe reads E=0 in 449 valid eight-pixel groups, with unchanged textures/material/light; the estimated additive red term falls from a median 1.814 to 0.0120 before fog/postprocessing (R11G11B10 quantization and adjacent-pixel probe lanes apply). No material override or shader clamp was applied. The separate terrain fix below resolves the captured cave gaps; these checks do not establish full-game correctness or sustained frame rate.
- **Environment mip experiment (rejected):** a restricted-mip sampling A/B did not fix the skin. The captured 128-square environment cube contained no NaN/Inf. The experimental code was removed.
- **Spatial upscaler:** the configured 24 NDSR compute keys are alternative shaders for one dispatch, not 24 dispatches. All have one sampled input (slot 0), one output image (slot 1), and read-only weights (slot 2); none reads temporal history. The captured `14a8aaf3e0a9edbd` variant is linear input/output, and the former pink skin already existed in the main colour pass before upscaling. The Vulkan replacement now validates this contract, honors the push-bank 24 rectangles and view mip/layer, and retains the original dispatch when replacement cannot execute. The default is bilinear; opt-in hardware Catmull-Rom uses the [audited linear-output profile metadata](../../../docs/reference/rendering.md#vulkan-cubic-upscaling-with-a-proven-colour-contract). Both are spatial approximations of the network. **Open:** eight encoded-output variants still need colour encoding; the current replacement preserves its previous colour approximation. They are `131d7dcc054f92b9`, `eb0af4c68c522092`, `0e351bd8ef324466`, `446761e211ec30d8`, `8df4d4ba8fa94292`, `1c144a902af468de`, `c8910045dc5b59af`, `d19ea940b265456f`.
- **Original network correctness (resolved for the captured Android variant):** enabling native `14a8aaf3e0a9edbd` first left only the output's clear colour: its storage image lacked Vulkan storage usage. [Native-resource promotion](../../../docs/reference/rendering.md#vulkan-storage-use-preserves-an-existing-render-target) restores writes while preserving rendered data. The resulting tiled/wavy image then exposed [logical 32-lane shuffles addressing the wrong half of Adreno's 64-lane subgroup](../../../docs/reference/shaders.md#nvidia-warp-exchanges-inside-wider-vulkan-subgroups). Corrected input/output float captures are finite and coherent; the repeated block pattern is gone. The original shader clamps reconstructed neural luma to 0–128, then restores chroma and decodes colour; this is not a final RGB clamp or exposure normalization. There is no temporal history in this kernel.
- **Native network performance remains open:** Mac defaults to the game's network lowered through Metal matrix operations; MetalFX is opt-in. Android's stock driver exposes FP16 and 64-lane subgroups but no cooperative-matrix extension. [Exact software HMMA shuffle transport](../../../docs/reference/shaders.md#exact-software-hmma-transport-through-subgroup-shuffles) passes actual Adreno bitwise comparison and improves the network substantially, but a 120-frame run without pass dumps still records 36–44 ms GPU elapsed versus about 14.5 ms on the bilinear path (roughly 24 ms extra; whole-frame timing, not a pure kernel benchmark). The game switches interval 2→3 during native execution and returns to 2 afterwards. Compiler statistics retain 6% occupancy, 40 full-precision registers and zero spills after streaming; about 53,000 instructions remain. Native dispatch therefore remains a diagnostic (`DM_VK_UPSCALER_NATIVE=N`, traced countdown; `-1`, quiet indefinite; `0`, fast replacement). No 60 fps or whole-game equivalence is claimed.
- **Terrain popping / black triangles (resolved in the captured Android cave):** depth-prepass GS `5d537f7630ec3671` compacts surviving triangles into the later colour draw's indirect index buffer. GPU capture found no foreign or invalid triangles, but each survivor appeared three times and counts exceeded source capacity. Changing only `OutputVertices` from 3 to 4 changed duplication to four copies, while the shader still emitted three vertices. Source-index replay independently removed the gaps in repeated off/on comparisons. This isolates repeated Adreno GS side effects. The general [primitive ownership repair](../../../docs/reference/shaders.md#adreno-geometry-side-effects-executed-once-per-primitive) preserves culling, shading and raster output while performing the index stores and count atomic once. The rebuilt runtime removes the black ceiling shards (`gs-candidate-cave.png`). Post-fix capture `index_dump_7153` contains 662 matched records, 68,074 source triangles and 24,449 generated triangles, with zero duplicate excess, foreign triangles, invalid indices or capacity overflow. This validates the active direct, single-instance triangle path; unsupported topology/instancing retains prior behavior with diagnostics. `DM_VK_ORIGINAL_INDEX` and `DM_VK_INDIRECT_TOUCH` remain disabled diagnostics.
- **Remaining cost:** a stationary docked baseline had about 6,562 draws, 13.3–13.8 ms CPU replay (3.4–3.6 ms descriptor work) and 22–23 ms GPU busy time, with zero steady-state texture uploads. These costs overlap and must not be added. Later instrumented/moving scenes are not comparable performance tests. The runtime is native ARM64, while GPU commands and shaders need translation. The 967 MHz GPU floor in the existing environment was refused by `su`; it was not active during these captures.
- **Asynchronous CPU hint accounting (fixed; device benefit pending):** `async-first-baseline.log` reports accepted Android 15 CPU hints of 0.79 ms while title replay costs 2.34 ms, and 3.33 ms while replay in a later load/gameplay window costs 16.23 ms. [ADPF now retains measured replay work](../../../docs/reference/frame-rate.md#android-cpu-hints-retain-asynchronous-replay-work) and includes both known frame threads; an active 60 fps work target alone did not correct the missing duration. Focused tests pass, but this does not yet establish faster frames.
- **Completed-frame ADPF candidate (device A/B run; no FPS gain established):** [matched completed-frame hints](../../../docs/reference/frame-rate.md#android-performance-hints-from-matched-completed-frames), enabled at startup by `DM_ADPF_COMPLETE=1`, pair exact CPU frame IDs with calibrated GPU endpoints. Host/threaded/sanitizer checks and device acceptance pass. ## Pause menu: frame cap and resolution (Android, 2026-11-08)

- **How the game steps its time:** its frame-rate controller (`main+0x204a18`, once a frame from `main+0x203718`) reads the frame's measured time, presenter `+0x128` in ticks of the 31.25 MHz counter (frame start `+0xf0` to the later of the submission and the GPU's end, the latter through `nvnDeviceGetTimestampInNanoseconds`, `main+0x2045bc`), wants interval `floor(vsyncs - 0.2) + 1` clamped to 1..3, steps up after 2 such frames and down after 6, and sets it through `main+0x204c00` → `nvnWindowSetPresentInterval`; it also stores `60 / interval` (presenter `+0xe0`, `+0x50` in its settings). The game advances by the interval it chose: when the host's adaptive rate presented it at 40 fps with the game at interval 1 it ran at two thirds of its speed. The pacing wait is outside what the controller measures, so presenting it slower does not make it choose a longer interval.
- **Frame cap** (menu row Off / 60 / 30, `settings.txt fpscap=`): an `OBS_FRAME_CAP` gate (`patches.py`, `main+0x204a44`, right after the controller loads `+0x128`) lengthens that reading to the capped period (`hle_framecap.c`), so the controller picks interval 2 itself, with its own hysteresis, and steps by it. A frame longer than the cap reads as itself (the game still drops to 20 fps where it would). 60 is the same as Off here (the game never goes past 60). 40 is not offered: the controller counts whole 60 Hz vsyncs, so 40 fps is an interval it cannot name and would run slow. Measured on the Odin 3 (handheld, outdoor smash route): `[framecap] game time` (Σ interval / 60 against the wall clock) 0.999-1.004 of real time at 30 fps, 597-600 of 600 frames at interval 2 within 2 frames of the change, on-screen p99 33.3 ms; Off: 0.99-1.00 at 60 fps.
- **Resolution** (row Perf / Balanced / Quality / Max, `settings.txt res=`; it replaces the Mode row): the renderer's settings (`main+0x4c5228` builds sead-style parameter objects, value at `+0x64`; the game loads them from its files right after) include `MaintainGpuPercentage` (90 from the file: the GPU share of the frame its dynamic resolution holds) and `NdsrUpscaleMinRate` / `MaxRate` (1.375 / 2: the upscale range, so 960x540 to 1397x786 for the 1920x1080 handheld picture). `OBS_RES_PARAM` gates on the stores of those objects hand them to the host, which writes the level's value over the game's own whenever the game writes one (only while the object keeps its vtable). Perf: lowest rate 1.667 (at most 1152x648, 1120x630 measured) and 70 % of the GPU target; Balanced: the game's own; Quality: lowest rate 1 (up to 1920x1080 where the GPU target allows); Max: docked (the game's own docked picture, scaled to the screen). The upscale range is read when the game sets up an area, so a level reaches the render size at the next load; the mode change reaches the game as the menu closes.

## Open

- **Video decoding:** the guide movies are VP9 and play (a 180-picture clip on loop in the tutorial's panel, read back as NV12). The player also imports the VP8, H.264 and AV1 decoders: VP8 and H.264 are served too (checked by `t_codec_video` only), AV1 is not ([`nn::codec` video decoders taken over](../../../docs/reference/movies.md#nncodec-video-decoders-taken-over)).
- **The gameplay picture:** the mining tunnel matches a YouTube capture of the same spot ([Rendering](#rendering) 7); nothing past the tunnel's first minute has been compared.
- Full shader build (about 75 minutes on the Mac from an empty cache): 22,852 of 22,852 shaders on chain 6f41726ef36d (SUATOM decoded; 22,850 on chain 3c66991eb439). Chain 9a0726336e9d had 22,834: the Metal compiler refused 11 (too deeply nested jump tables) and 5 used BRXU or REDUX ([Ampere shader code](../../../docs/reference/shaders.md#ampere-shader-code-switch-2)); 2 still do not translate (0x593).
- `oe::GetCurrentGraphicsScale`: which tier the console reports in which mode is not measured (the host answers 0 handheld, 1 console). The game uses it as a quality tier, not for correctness: a byte of its graphics settings and a renderer parameter of 0, 9 or 13 (`hle_oe.c`).
- The 9 GB pool.
- The terrain's stores through loaded pointers keep reaching memory pools the host learns only afterwards (12 in a 17,700-frame session); each such miss is checked against the uniform shadows that relied on it, and none so far covered a written page ([Global memory at an address loaded from memory](../../../docs/reference/shaders.md#global-memory-at-an-address-loaded-from-memory), Open).
- **Frame rate in busy scenes:** the game picks its own present interval: 3 (20 fps) in its cutscenes, and 1 ↔ 2 (60 ↔ 30 fps) by its frame-rate controller (`main+0x204a18`; settings at `0x703f72b200`: interval 1 to 3, margin -0.2, 2 late frames to go up, 6 to come back). It measures each frame from its start (`+0xf0`) to the later of its submission and the GPU's end (`+0x128`, ticks) and wants interval 2 from 1.2 vsyncs (20 ms). On the Mac (M4 Pro) that measure sits at 17 ms a frame (p90 24): the host's translation (CPU, 5-9 ms) before the GPU's 10-13 ms. The upscaler's HMMA through `simdgroup_matrix` ([Ampere HMMA through simdgroup_matrix](../../../docs/reference/shaders.md#ampere-hmma-through-simdgroup_matrix)) cut the switches by about a fifth; the geometry runs' dependency check, quadratic in the run's length ([Geometry dependency checks skip read-only pairs](../../../docs/reference/shaders.md#geometry-dependency-checks-skip-read-only-pairs)), was about 8 % of the submitting thread, and making it linear cut them from 30 to 12 on the same scripted route. Entering a level stalled for 1.3 s on GPU drains, one or two per geometry draw ([CPU reads after a drain wait only for later writes](../../../docs/reference/rendering.md#cpu-reads-after-a-drain-wait-only-for-later-writes)); one CPU-bound build frame of 195-280 ms remains. Measured without `sample` attached: it suspends the process and makes the submitting thread look stalled. Its geometry draws are mesh draws ([Mesh geometry groups sized to the vertex output](../../../docs/reference/shaders.md#mesh-geometry-groups-sized-to-the-vertex-output)): translation 9.9 → 7.2 ms a frame, GPU p50 11.8 → 9.0 ms on the scripted route. Open: the rest of the translation time in the busiest views (argument encoding, render pass setup), where translation and the GPU together still miss a vsync now and then.
- The NVN2 device values the driver reads from the GPU at run time (17 items: scratch scale factors, L2 size, texture layers and sizes, linear stride alignment, pool page size, …) are still the Switch 1 ones; the constant ones are NVN2's ([The Switch 2's device values](../../../docs/reference/nvn-objects.md#the-switch-2s-device-values)).
- iOS: longer sessions, current main and other devices remain unvalidated; see the initial [community report](#ios-community-report).
